            System Guide

            Everything in the backend of the KitsoHub Career Decision System™ — how data flows, how scoring works, what each component does, and how to interpret what the system produces.

            How the system works — end to end
            5-step learner journey
            1
            Learner profile + APS entry
            Name, school, grade, email, consent captured. Subjects selected from the NSC catalogue (8 slots: Home Language, FAL, Maths stream, 3 electives, 1 optional elective, Life Orientation). Marks entered → APS calculated live using best 6 non-LO subjects — LO excluded per SA institution standard. Points scale: 80–100=7, 70–79=6, 60–69=5, 50–59=4, 40–49=3, 30–39=2, 0–29=1.
            2
            Aspiration selection
            Learner selects up to 3 study directions from 12 career clusters. Each card shows the APS status badge (met or gap). Selections are stored as window.chosenAspirations[] and feed directly into the scoring engine as pre-weights (Fix C).
            3
            Gap screen
            For each chosen direction: current APS vs minimum APS vs stretch APS displayed as a bar. Improvement levers shown per subject (which mark bracket to hit, how many APS points it adds). Subject requirement warnings checked against CLUSTER_SUBJ_REQS — flags missing Maths, Life Sciences, Physical Sciences, or key subjects for each cluster.
            4
            28-question clarity check
            4 short sections. The quiz is a support layer only: it helps explain study preference, route confidence, and CV strengths. It does not override APS, subjects, or gateway requirements.
            5
            Profile generation
            Final cluster ranking → recommended primary, secondary, and backup directions (using chosen aspirations as primary filter). Readiness level calculated from discipline/logic/organise/pathway signals. Subject warnings, CV starter, APS gap engine, learning style profile, university list, and career explorer all rendered from the recommended direction — not the raw quiz winner. Saved to cohort log.
            Scoring engine — 4-layer pipeline
            Applied in this exact order inside compute()
            // Layer 1 — Raw quiz accumulation cs[cluster] += answer_option_weight // per question answer // Layer 2 — Normalise by signal pool size cs[cluster] = (cs[cluster] / POOL[cluster]) * 100 // POOL: stem=47, health=12, comm=48, admin=82, built=58 ... // Prevents admin (pool 82) from structurally beating stem (pool 47) // Layer 3 — Subject signal injection // Maths pts → +STEM, +ICT, +Commerce; Life Sci pts → +Health, +Agri cs[cluster] += subject_pts_bonus * cluster_weight // Layer 4 — Aspiration pre-weight cs[chosen[0]] += 15 // primary choice cs[chosen[1]] += 12.75 // secondary choice cs[chosen[2]] += 10.5 // tertiary choice // Layer 5 — APS calibration (on normalised scores) // Met: +surplus*0.6 bonus | Gap ≤5: -gap*0.5 | Gap ≤12: -gap*1.2 | Gap >12: -gap*2.0
            Why normalisation matters
            The question bank has unequal coverage: some routes naturally appear more often than others. Normalisation prevents generic answers such as “organised” from overpowering the real decision factors: selected direction, APS, subjects, and gateway requirements.
            Subject injection — why it matters
            The quiz asks about work style and preferences. It does not directly ask "do you have Maths?" — but the subjects a learner has are the clearest signal of fit and access. Subject injection seeds cluster scores from actual marks before quiz answers are counted. Maths at 7pts adds +14 to STEM, +10.5 to ICT, +8.4 to Commerce. Life Sciences at 7pts adds +14 to Health, +8.4 to Agri.
            12 career clusters
            APS minimums · stretch targets · signal pool sizes
            Readiness classification
            Derived from quiz dimensions, not APS alone
            readiness_score = discipline * 3 + logic * 2 + organise * 1.5 + uni_pathway * 3 + uot_pathway * 1.5 + tvet_pathway * 0.5 normalised = min(100, (readiness_score / 130) * 100) if normalised >= 60 → High readiness (university pathway likely) if normalised >= 35 → Needs structured support (UoT / extended programme) else → Alternative pathway recommended (TVET / bridging)
            Readiness is intentionally separate from APS. A learner can have APS 32 but low readiness signals (low discipline, low logic scores) — the system will still recommend a university pathway but flag that structured support is needed. Conversely, a learner with APS 20 can show high discipline and practical aptitude — the system recommends TVET but notes the strong work habit.
            Recommended direction logic
            How primary / secondary / backup are chosen
            // If learner chose directions on aspiration screen: primary = chosen direction with highest quiz-normalised score secondary = chosen direction with second-highest quiz-normalised score backup = chosen third direction (if 3 chosen) OR best quiz-ranked unchosen cluster that meets APS // If no direction is selected: primary = top cluster from normalised + weighted scoring secondary = second cluster backup = best APS-met cluster not already in primary/secondary // Backup never defaults to admin — it uses quiz rank + APS fit
            Data model — what is stored
            Two storage keys, browser-local via window.storage
            STORE: botsh_cps_v5 Cohort log
            Array of learner objects. Each entry contains: name, school, grade, mentor, date, email, parentEmail, consentCaptured, aps, pathway (uni/uot/tvet), cluster (primary), cluster2 (secondary), gap (APS points to top cluster), keySubj, style (learning style), summaryText, subjects[] (array of {k, name, lo} — used by progress tracking to load the right subject inputs). The subjects[] field was added in v15 so progress entries map to real subject names, not slot labels.
            PSTORE: botsh_progress_v1 Progress tracking
            Object keyed by "learnerName||school". Each learner record contains: learnerName, school, baselineAps, baselineCluster, entries[]. Each entry: year, term (T1/T2/T3/Mid/Final), periodKey, marks{} (subjectKey → {name, lo, mark}), aps (recalculated), savedAt. Progress APS recalculated from best 6 non-LO subjects — LO excluded.
            System tabs and what each does
            5 tabs, all in a single HTML file
            Assessment
            The main 5-step learner journey: profile → APS → aspiration selection → gap screen → 28-question readiness assessment → results profile. Each step is a separate screen within the assessment tab. The full profile card is print/PDF ready.
            Cohort log
            Tabular view of all completed assessments. Shows APS, pathway, top cluster, 2nd cluster, APS gap, key subject, learning style per learner. Export to CSV. Stats strip: total assessed, university-ready count, UoT+TVET count, most common cluster.
            Progress tracking
            Quarterly mark entry per learner (no re-assessment needed). Select learner → pick term → enter marks → APS recalculated. Trajectory view shows APS at each period, subject mark table with delta chips, and auto-generated insight blocks (new pathway unlocked, declining subjects, flat trajectory flags). Export to CSV.
            Learner dashboard
            Live overview card per learner combining baseline profile + latest progress entry. Shows APS trajectory KPIs, subject sparkbars with trend indicators, pathway readiness meters, and inline mark update — enter new marks directly on the dashboard without switching tabs. Filterable by school and pathway. Sortable by name, APS, improvement, or date.

            This page. Full documentation of the backend: scoring pipeline, data model, cluster reference, readiness logic, direction selection algorithm, and storage schema.
            Exports available
            All exports are CSV, downloaded locally
            Cohort log CSV — one row per learner, all baseline fields. Progress CSV — one row per term entry per learner, with APS delta and all subject marks as dynamic columns. Dashboard CSV — one row per learner combining baseline + latest progress, for reporting and sharing with school or programme leadership.
            Google Sheets backend — how to connect
            Facilitator report via Google Apps Script · WEB_APP_URL configuration
            Step 1 — Create the Google Sheet
            Create a new Google Sheet. Add one sheet named Responses. The Apps Script will write headers automatically on first submission.
            Step 2 — Deploy the Apps Script
            In your Google Sheet, open Extensions → Apps Script. Paste the script below. Click Deploy → New deployment → Web app. Set "Execute as: Me" and "Who has access: Anyone". Copy the Web App URL.
            // Google Apps Script — paste into your Sheet's Script Editor function doPost(e) { try { var data = JSON.parse(e.postData.contents); var ss = SpreadsheetApp.getActiveSpreadsheet(); var sheet = ss.getSheetByName('Responses') || ss.insertSheet('Responses'); // Write headers on first row if empty var headers = ['Timestamp','Learner Name','School','Grade','Facilitator', 'Learner Email','Parent Email','Consent','APS','Pathway','Readiness Level', 'Readiness Score','Final Direction','Final Status','Primary Blocked', 'Primary Direction','Primary Status','Primary Gap', 'Secondary Direction','Secondary Status', 'Backup Direction','Backup Status', 'Selected Directions','Q1 Study Now','Q2 Statuses', 'Q3 Improvements','Q4 Safe Backup','Q5 Final', 'Key Subject','Learning Style','Work Dimension','System Version']; if (sheet.getLastRow() === 0) sheet.appendRow(headers); // Write data row sheet.appendRow([ data.timestamp, data.learnerName, data.school, data.grade, data.facilitator, data.learnerEmail, data.parentEmail, data.consentCaptured, data.apsScore, data.pathwayTier, data.readinessLevel, data.readinessScore, data.finalRecommendedDirection, data.finalRouteStatus, data.primaryWasBlocked, data.primaryDirection, data.primaryStatus, data.primaryGap, data.secondaryDirection, data.secondaryStatus, data.backupDirection, data.backupStatus, (data.selectedDirections||[]).join(', '), data.q1_studyNow, data.q2_directionStatuses, data.q3_subjectImprovements, data.q4_safeBackup, data.q5_finalRecommendation, data.keySubjectToImprove, data.topLearningStyle, data.topWorkDimension, data.systemVersion ]); return ContentService.createTextOutput(JSON.stringify({status:'ok'})) .setMimeType(ContentService.MimeType.JSON); } catch(err) { return ContentService.createTextOutput(JSON.stringify({status:'error',message:err.toString()})) .setMimeType(ContentService.MimeType.JSON); } }
            Step 3 — Set WEB_APP_URL in this file
            In this HTML file, find the line const WEB_APP_URL = ''; near the top of the submission engine section and replace the empty string with your deployed Web App URL. Save and re-open the file. All future submissions will POST the full facilitator report to your Sheet automatically.
            What the facilitator report contains
            The full report object includes: learner identity (name, school, grade, email, parent email, consent, facilitator, date), APS and pathway tier, readiness level and score, selected aspirations, all 5 pipeline answers (Q1–Q5), per-direction diagnostic (all 12 clusters: route status, APS gate, gateway issues, quiz score), subject marks with points, improvement plan (up to 4 subjects with gain), learning style and work dimension, and system version. The learner never sees this data — they receive only the clean learner summary modal.
